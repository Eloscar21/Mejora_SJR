# HU-12: Formulario de creación de reportes

## Recorrido

Tras iniciar sesión, `src/app/index.tsx` abre `/crear-reporte` en el Stack de Expo Router.
`src/app/crear-reporte.tsx` compone la pantalla: inyecta el servicio y las categorías al
hook y entrega únicamente datos y callbacks usados por `ReporteView`.

- `src/models/Reporte.ts`: payload con las siete llaves exactas de HU-12, categorías y estado de edición.
- `src/views/ReporteView.tsx`: TextInputs, captura **manual** de coordenadas, selector de categorías con botones de radio, carga, error y confirmación. No tiene hooks ni HTTP.
- `src/viewModels/useReporteViewModel.ts`: campos, validación, conversión de coordenadas a números, envío, bloqueo de solicitudes simultáneas y reintentos. Recibe `apiService` por parámetro obligatorio.
- `src/services/contracts/IReporteApiService.ts`: contrato mínimo `crearReporte` (ISP).
- `src/services/api/ReporteApiService.ts`: POST `/reportes`, serialización, token Bearer si existe, errores HTTP y confirmación `success: true`.
- `src/providers/reporteDependencies.ts`: crea la implementación HTTP e inyecta el almacenamiento existente. Lee `EXPO_PUBLIC_API_URL` (incluye `/api`).
- `src/constants/categoriasReporte.ts`: punto de configuración del catálogo real, actualmente pendiente y vacío.

SRP separa UI, estado y transporte. DIP evita que el hook importe implementaciones concretas:
depende de `IReporteApiService`. DI ocurre al pasar la instancia en la composición de pantalla.
Los objetos entregados a la Vista contienen solamente campos que dibuja, sin servicios o sesión.

## Validación y comportamiento

Título y descripción obligatorios. Latitud entre -90 y 90; longitud entre -180 y 180.
Cero es válido; un campo vacío no se convierte accidentalmente en cero. Se admiten decimales
con coma o punto. La categoría debe existir en el catálogo inyectado y tener un ID entero positivo.
Dirección y evidencia son opcionales; evidencia, si se escribe, debe ser una URL HTTP(S).
No se suben fotos ni se solicita GPS en esta entrega.

La edición conserva las mismas llaves PascalCase. Las coordenadas son texto durante la escritura;
solo se convierten al preparar el JSON. No se agregan `IdUsuario`, `IdEstado` ni fechas.
Los campos quedan bloqueados durante el envío y se conservan si falla. Tras éxito se ofrece
crear otro reporte. Una respuesta tras desmontar la pantalla no publica nuevo estado.
No hay reintentos automáticos ni cancelación HTTP; el bloqueo local no sustituye la idempotencia del servidor.

## Pendientes reales de integración

1. Entregar el catálogo real `{ IdCategoria, Nombre }` de SQL Server o confirmar su endpoint.
   No se inventaron IDs de producción. Mientras esté vacío, se informa la ausencia y se desactiva el envío.
2. Alinear el backend: `ReporteController.js` exige `IdUsuario`, pero el payload solicitado de HU-12
   lo omite. Actualmente responderá 400 aunque los siete campos sean válidos. El backend debe resolver
   al ciudadano desde una sesión verificada, o debe acordarse explícitamente un nuevo contrato.
   Adjuntar un token no resuelve por sí mismo esta incompatibilidad. No se modificó el backend.
3. Probar el flujo con API/SQL Server y dispositivo reales una vez resueltos esos puntos.
   En celular físico, configurar una URL del servidor accesible desde su red.

## Verificación

`npm test` prueba validaciones, llaves y tipos del payload, cero, doble envío, estados, reintento,
serialización HTTP, token y respuestas inválidas mediante servicios simulados. Los IDs de prueba
no se usan en la aplicación. `npm run typecheck` revisa tipos. Expo regenera los tipos de rutas
al iniciar con `npm start` después de cambiar de rama o añadir una ruta.

El renderer usado para probar el hook emite un aviso de deprecación; no forma parte del runtime móvil.
No se considera verificado el guardado real en SQL Server con estas pruebas aisladas.
